01 · The problem

Three failures, one cause

During a medical emergency in India, three things go wrong independently. Families don't know which hospital has an open bed, ICU slot or blood unit right now. Ambulances sometimes reach a hospital that then can't accept the patient, losing critical time. And hospitals get no advance warning, so they scramble instead of preparing.

All three happen because hospitals, ambulances, blood banks and traffic control work as disconnected islands with no shared live data.

GoldenLine is a coordination layer, not a replacement for 108 dispatch or a hospital's own system.

02 · What I built

One pipeline from the first call to discharge

A case can start two ways: a family presses SOS in the app, or an ambulance helper starts it on the spot after a 108 call. From there it's the same pipeline.

  1. Case createdFrom the family app, or by a registered ambulance helper with a mandatory next-of-kin number
  2. On-scene assessmentThe helper logs symptoms by voice or tap
  3. Hospital rankingThe closest hospital with the right specialty, sorted by travel time, distance and rating, with no black-box model
  4. Bed lockA short-lived hold on the chosen bed so no one else can take it
  5. Route and bloodRoute suggestions, plus a blood-unit check when needed
  6. Hospital preparesThe receiving team gets prep actions before arrival
  7. QR handoffArrival confirmed by QR; the bed count updates automatically
  8. Family trackingA read-only SMS tracking link, then discharge feedback
03 · Key ideas

The details that make it safe to rely on

Two ambulances can never claim the same last bed

The bed lock is a single guarded database statement: a lock is inserted only if the hospital's live capacity is still greater than its active locks. The database settles the race, so two simultaneous requests for the last ICU bed can't both win, and every collision is recorded.

A background supervisor, but only a human resolves

The Control Room watches the pipeline underneath everything: an ambulance whose location stops updating, two critical patients heading for the same last bed, a reported bed that was quietly given away. Every flag goes to a named human. Nothing is silently auto-resolved.

Privacy and abuse prevention built in

Staff sign in with hashed passwords (PBKDF2) and a real forgot-password flow, and families use one-time codes. Access is scoped by role, duplicate cases auto-merge, unusual request rates are flagged, and data can be deleted on request. The family sees which ambulance is coming and where it is, but deliberately not the driver's phone number, to avoid a harassment risk.

Honest limits

  • It's a prototype. It's seeded with 25 real Dindigul hospitals, but bed and blood data are demo values, and it isn't connected to live 108 dispatch or hospital systems.
  • Out of scope on purpose: if no registered ambulance with the app is present, the platform doesn't engage. An earlier family self-transport idea was scrapped as unsafe.
05 · How I built it

My role, and how the AI tools were used

I build with AI development tools and I'm open about it. My part is the work the tools can't do alone: choosing the problem, writing the specification and the rules every change must respect, splitting the build into small tested phases, and checking each result against the project's own output.

For GoldenLine, I wrote the functional requirements plan first and built it one requirement per phase, each with its own tests before the next began. That is why the project could grow from 17 to 23 requirements without breaking what already worked.

Every number on this page can be traced to a file in the repository (the README records each phase and its tests).
